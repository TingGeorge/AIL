# ALL IN LIFE 下一階段 RFC：Budget OS、團戰與社群情報

- 狀態：產品規劃草案
- 版本：v0.2
- 日期：2026-09-04
- 依據：現有 PRD、Game UI MVP、團隊討論與 FUTUREMODE 視覺規格

## 1. 結論先行

這批想法不是幾個零散功能，而是能把 ALL in life 從「低價搜尋器」升級成三層產品：

1. **Budget OS**：先知道這個月還能花多少，再決定這一餐或這次採買能花多少。
2. **Agent Hunting**：CP 值獵人找通過限制的低成本方案；零元獵人找費用為零但條件透明的資源。
3. **Squad Intelligence**：可信的社群情報與合購需求，讓個人無法取得的量價優勢變成團隊戰利品。

最重要的產品原則是：**最低價格不能凌駕安全、份量、資格、個人禁忌與證據。**

## 2. 命名建議

| 內部概念 | UI 名稱 | 說明 |
|---|---|---|
| Paid Agent | CP 值獵人 | 搜尋付費但低成本的可比方案 |
| Free Agent | 零元獵人 | 公開品牌名稱；「白嫖模式」可作遊戲文案，不建議成為正式 Agent 名稱 |
| Extreme saving | 最窮酸 | 最低成本優先，但不降低安全與硬限制 |
| Balanced saving | 可以過活 | 成本、時間、偏好與便利平衡 |
| Group buying | 團戰合購 | 邀請制小隊共同湊量與拆分 |
| Community report | 生存情報 | 價格、庫存、品質、資料錯誤與安全事件的總入口 |

## 3. 新的產品架構

```text
月度資金設定
  ├─ 必要固定支出
  ├─ 類別預算袋
  ├─ 剩餘天數與安全墊
  └─ 個人硬限制／軟偏好
          ↓
本次任務：快速填寫｜文字｜語音
          ↓
可編輯的「目前理解」
          ↓
CP 值獵人 ║ 零元獵人
          ↓
正規化 → 證據閘門 → 硬限制 → 模式排序
          ↓
個人方案｜團戰方案｜社群風險訊號
```

「月預算」是上層資金策略；「單次預算」仍是本次任務的硬限制。兩者不可合併成一個模糊滑桿。

## 4. 輸入體驗

### 4.1 入口設計

設定區使用三個入口，共用同一份解析結果：

- **快速填寫**：可視化欄位，適合精確控制。
- **文字描述**：例如「本月只剩一萬，要撐 23 天，不吃牛，晚餐兩人 250 內」。
- **按住說話**：錄音後顯示逐字稿；玩家確認後才解析與搜尋。

不把語音做成另一套流程。語音只是自然語言的輸入方式，轉錄後必須回到同一個「目前理解」畫面。

### 4.2 解析摘要

摘要分三層：

1. **硬限制**：金額、份量、人數、日期、區域、距離／時間、不能吃／用、資格。
2. **軟偏好**：口味、品牌、可外帶、可等待、願意分裝、便利性。
3. **未知／待確認**：語音辨識不清、未提供或來源不足的欄位。

每個解析標籤都能點擊修改。語音信心不足的欄位必須醒目要求確認，不能靜默猜測。

### 4.3 語音隱私

- 預設只保存本工作階段的逐字稿，不保存原始音檔。
- 送出轉錄前顯示麥克風狀態與用途。
- 使用者可清除逐字稿。
- 不從聲音推測年齡、性別、健康狀況或情緒。

## 5. Budget OS

### 5.1 月度設定欄位

- 本月可用生活費。
- 本月起訖日與剩餘天數。
- 已知固定支出：房租、水電、通訊、交通等。
- 安全墊：不可動用金額或百分比。
- 類別預算袋：食品、日用品、活動、交通、其他。
- 每日／每週建議上限。
- 個人或家庭人數。

### 5.2 運算

```text
可分配生活費 = 月度總額 - 固定支出 - 安全墊
類別剩餘額 = 類別預算 - 類別已用額
每日可用額 = 可分配剩餘額 / 剩餘天數
本次建議上限 = min(使用者任務上限, 類別剩餘額, 模式建議值)
```

系統可以提出建議，不能未經同意改動硬上限。

### 5.3 生存模式

#### 最窮酸

- 先滿足安全、份量、禁忌、資格與距離／時間。
- 主要排序：總可比成本。
- 次要排序：單位成本、資料新鮮度、等待時間。
- 願意分裝、合購、較長等待可獲得較高匹配，但必須由玩家設定。

#### 可以過活

- 先滿足所有硬限制。
- 在預算內平衡成本、時間、份量、偏好與可信度。
- 不用黑箱綜合分數；卡片顯示「貴 NT$20，但少走 12 分鐘」等可理解理由。

### 5.4 個人規則

分成兩組，避免把偏好錯當成安全條件：

- **絕對排除**：不吃牛／豬、素食、宗教限制、使用者明確提供的過敏原、無障礙需求、會員資格缺失。
- **偏好加分**：辣度、品牌、口味、可外帶、環保包裝、可等待、願意分裝。

健康相關輸入只作排除與提醒，不提供診斷、營養或醫療判斷。

## 6. 團戰模式

### 6.1 為什麼值得做

團戰能產生單人搜尋做不到的價值：

- 湊到買一送一、滿額折扣或批發門檻。
- Costco 等大包裝拆分，降低單位成本與浪費。
- 聚合固定月份需求，向商家提出團購價。
- 將「搜尋到優惠」推進為「真的湊得到量」。

### 6.2 第一階段：邀請制熟人團

MVP 只做已知關係的邀請連結或小隊碼：

1. 建立團戰，選擇商品／方案。
2. 設定目標數量、最低成團人數、每人上限與截止時間。
3. 分享邀請連結。
4. 成員填寫承諾數量與可接受替代方案。
5. 系統顯示是否達標、預估個人成本與拆分方式。
6. 團主前往外部來源完成購買；平台不代收款、不保證履約。

### 6.3 暫不做陌生人揪車

陌生人共乘會引入人身安全、身份驗證、保險、責任、路線、定位與交通法規。下一階段最多支援：

- 熟人小隊記錄預估分攤。
- 開啟既有合規叫車／大眾運輸服務。
- 不做陌生人司機／乘客媒合，不提供導航。

### 6.4 團戰結果卡

除一般結果欄位外，增加：

- 個人價與成團價。
- 最低成團人數／數量。
- 已承諾進度。
- 截止時間。
- 分裝單位與地點描述。
- 會員或押金條件。
- 未成團風險與退出規則。

## 7. 社群情報與食安通報

### 7.1 回報類型必須分開

| 類型 | 例子 | UI 與系統處理 |
|---|---|---|
| 資料錯誤 | 價格過期、連結失效 | 進入資料審核，不等同負評 |
| 品質體驗 | 份量少、等待久、味道不符期待 | 顯示為主觀體驗，可按有幫助 |
| 優惠情報 | 新品、折扣、買一送一 | 要求來源、照片或時間，過期自動降權 |
| 安全事件 | 不潔、疑似異物、身體不適 | 高風險通報流程，與評論分離 |

### 7.2 安全事件呈現

不能寫成「這家店造成食物中毒」，除非有官方資訊。UI 使用分級語言：

- **單一使用者回報 · 尚未驗證**。
- **近期多筆相似回報 · 平台審查中**。
- **商家已回應**。
- **官方公告／裁罰／召回**。

結果卡可顯示醒目「近期安全回報」，但點開後必須看得到回報數、時間範圍、驗證狀態與官方來源。單一未驗證回報不直接永久下架商家；可以暫時降低推薦信心並要求使用者自行確認。

### 7.3 回報表單

- 發生日期與大約時段。
- 品項／方案。
- 回報類型。
- 簡短描述。
- 選填證據：收據、照片、公開來源。
- 是否願意讓商家回應。
- 明確提醒不要公開電話、地址、病歷或其他敏感資料。

涉及嚴重身體不適時，介面應優先建議尋求適當醫療或官方通報管道，而不是讓社群投票代替處理。

## 8. 信譽系統

### 8.1 原則

不要直接複製 Reddit 的單一 Karma。按讚容易形成同溫層、報復與商家操控。信譽必須以「可驗證貢獻」為主。

### 8.2 信譽事件

- 價格／時間資訊後續被官方來源確認。
- 過期情報被正確標記。
- 回報獲多位獨立使用者佐證。
- 商家或管理員確認資料修正。
- 重複、誤導、無來源或惡意回報則降低內部權重。

公開只顯示容易理解的等級：新手、情報員、可信獵人。精確風險分數保留在系統內，避免變成追逐數字的遊戲。

### 8.3 防濫用

- 新帳號與同裝置頻率限制。
- 同一商家集中回報偵測。
- 重複內容與圖片檢查。
- 商家不得用付費移除真實安全警示。
- 被檢舉者與商家皆有回應／申訴入口。

## 9. 商家合作與商業模式

### 9.1 建議的收入結構

#### 免費層

- 基本設定、既有資料瀏覽、食安與資料錯誤回報永遠免費。
- 每週有限次「重新查核網路來源」的 Agent 任務。

#### 玩家 Pro（價格待驗證）

- 更多 Agent 即時查核。
- 月預算自動追蹤與跨類別調整。
- 價格下降／免費名額／團戰成團提醒。
- 多個生活圈、家庭共享與歷史比較。

#### 商家層

- 提供可驗證的限時優惠與團購門檻。
- 需求趨勢與轉換分析，只提供聚合資料。
- 團購成交或導流服務費。
- 贊助曝光必須標示，且不得覆蓋自然排序、安全警示或證據狀態。

### 9.2 不建議一開始採用的方式

- 把免費／公益資源鎖在付費牆後。
- 單純依點擊向商家收費並影響排名。
- 商家付費即可移除負評或安全通報。
- 在沒有足夠回訪價值前直接限制為每週三次全部搜尋。

付費假設應先以訪談與行為資料驗證，不在 Hackathon 階段宣稱已確定。

## 11. 排序增量

個人與團戰結果分開呈現：

```text
個人結果：硬限制 → 證據閘門 → 模式排序
團戰結果：硬限制 → 證據閘門 → 成團可行性 → 個人成本
```

社群訊號只影響可信度與警示，不把按讚數直接當 CP 值：

- 官方來源權重高於社群回報。
- 新鮮且可驗證的情報高於熱門但過期的貼文。
- 安全事件獨立顯示，不被低價抵銷。
- Sponsored offer 必須先通過同一套硬限制與證據閘門。

## 12. UI 規劃

### 第一屏

- 左側：本月剩餘、剩餘天數、今日可用、安全墊。
- 右側 Mission Control：快速填寫／直接說切換、麥克風、需求文字、任務預算、人數。
- Mode Switch：最窮酸／可以過活。
- 「目前理解」在按下搜尋前直接展開，不藏在 Modal。

### Settings Sheet

使用右側 Sheet，不離開主流程：

- 月預算與固定支出。
- 類別預算袋。
- 絕對排除。
- 軟偏好。
- 團戰偏好：願意分裝、最大等待天數、僅限熟人邀請。

### Results

結果區增加三個視圖：

- 個人戰利品。
- 團戰可省。
- 生存情報。

卡片安全警示永遠高於優惠標籤；團戰價同時顯示原價、成團門檻與目前進度。

### 視覺演進

依 `fmdesign.md.md` 的 FUTUREMODE 觀察稿，下一版不再增加更多彩色 Dashboard 卡片，而是把目前的遊戲感收斂為：

- 黑白大區塊與不對稱編輯網格作主要骨架。
- 螢光綠只表示可行、通過與主要行動；紫色只表示模式或關鍵團戰狀態；黃色只表示待確認與風險。
- 月度資金、團戰進度與社群情報使用細線表格、橫向時間軸與大數字，不把每個欄位都包成卡片。
- 保留大量負空間、硬邊界與極大標題；避免玻璃、漸層、柔和陰影和泛用科技裝飾。
- 行動頁仍以工作介面優先，不照搬活動網站的長篇敘事首頁。

## 13. 分階段交付

### Phase A — Hackathon+（1 週）

- 文字／語音雙自然語言入口。
- 可編輯逐字稿與解析摘要。
- 月預算、剩餘天數、安全墊。
- 最窮酸／可以過活模式。
- 絕對排除與軟偏好。
- 使用固定資料完成 Demo，不先做登入與多人後端。

### Phase B — Invite Squad（2–3 週）

- 登入與暫時個人檔案。
- 邀請制團戰合購。
- 承諾數量、成團進度與拆分說明。
- 資料錯誤、優惠與品質回報。
- 最小審核後台與通知。

### Phase C — Trust Network（4–8 週）

- 安全事件通報與分級狀態。
- 可驗證貢獻式信譽。
- 社群來源進入 Agent 候選池。
- 商家驗證、團購門檻與清楚標示的贊助方案。
- 防濫用、申訴與稽核紀錄。

### 明確延後

- 陌生人揪車／司機乘客媒合。
- 平台內付款、代收與退款。
- 導航與即時位置。
- 醫療判斷與食物中毒因果認定。

## 14. 下一個可做的產品切片

建議下一個實作只做「Budget OS + 雙輸入」：

1. 首屏加本月 NT$10,000、剩餘 23 天與安全墊。
2. 加快速填寫／直接說 Tabs；語音產生可編輯逐字稿。
3. 加最窮酸／可以過活切換。
4. 加 3 個絕對排除與 3 個軟偏好示範。
5. 搜尋前顯示「目前理解」。
6. 讓現有兩 Agent 收到相同結構化輸入。

這個切片能在 90 秒 Demo 內講清楚，而且不必先承擔帳號、支付、陌生人安全與大型社群審核的風險。

## 15. 驗收條件

- 表單、文字與語音最後產生相同 schema。
- 語音逐字稿可修改，低信心欄位不可自動確認。
- 月預算與任務預算分開顯示、分開驗證。
- 兩種生存模式都不能繞過硬限制與證據閘門。
- 絕對排除與軟偏好在 UI、schema 與排序原因中可區分。
- 團戰 MVP 只允許邀請制，且不代收款、不保證履約。
- 安全回報與一般評論分開，單一回報清楚標示尚未驗證。
- 商家贊助不改寫自然排名，也不能移除安全警示。

## 16. 需要用研究回答的問題

- 使用者真正願意設定的是月總額、每週額度，還是各類預算袋？
- 「最窮酸」是否帶來幽默與認同，還是讓部分使用者感到被冒犯？
- 使用者願意為 Agent 查核、提醒、家庭共享或團戰哪一項付費？
- 熟人團戰最常見的品類是餐食、日用品、Costco 分裝還是交通？
- 食安警示需要多少獨立訊號才應影響推薦信心？
- 商家願意提供何種可驗證的團購門檻與即時資料？
