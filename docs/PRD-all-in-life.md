## 1. 一頁摘要

ALL in life 協助使用者在固定的圓山區生活圈內，依照預算、份量／人數、距離／時間與其他限制，快速找到可執行的生活選項。系統的核心不是把網路內容重新摘要，而是先套用硬限制，再以可比的成本排序，並讓每個結論都能回到來源與證據。

使用者不登入也能完成搜尋；註冊／登入是為了保存清單、收藏與設定，以及參與需要共享狀態的回報與揪團功能。帳號資料與搜尋輸入分離，音檔、逐字稿、需求與限制及搜尋歷史不保存。

候選紀錄在搜尋之前由爬蟲或 API 腳本事先匯入資料庫；執行期不上網搜尋。搜尋分兩階段：

1. **第一階段篩選**（不是 Agent）：對已匯入的候選紀錄套用證據閘門與硬限制，整個搜尋只跑一次。
2. **兩個並行 Agent 推薦排序**：**付費選項 Agent** 排序有直接支出的選項，**免費資源 Agent** 排序直接費用為零的資源；每筆附一句推薦理由，不刪除任何通過篩選的紀錄。

推薦結果進入五類 Dashboard：

- 食品
- 日用品
- 免費／公益資源
- 活動
- 交通

每類在 Demo 資料集準備 7–10 筆可操作資料。資料可以來自人工整理與網路搜尋的混合來源，但不得以沒有可讀證據的資料參與推薦排序。MVP 的主要成果是證明「同一個需求可以節省明確金額／比例」以及「至少找到一筆條件清楚的免費／公益資源」。

## 2. 問題、目標與產品原則

### 2.1 使用者問題

日常決策常同時受到預算、份量、人數、地點、時間與資格條件限制。資訊分散在商家頁面、活動頁面、公共資源公告與搜尋結果中，使用者需要自己確認：

- 價格是否真的可比；
- 份量或使用人數是否相同；
- 「免費」是否仍需要登記、會員或資格；
- 資訊是否過期；
- 推薦是否真的符合原本的距離與時間限制。

### 2.2 MVP 目標

1. 讓使用者用自然語言或最小表單說明需求與限制。
2. 以兩個並行 Agent 對通過第一階段篩選的候選紀錄做推薦排序。
3. **先篩硬限制，再以最低可比成本排序**；不因未知欄位而把資料當成便宜選項。
4. 以五類 Dashboard 呈現 7–10 筆有來源、有時間戳、有條件的結果。
5. 讓使用者在結果卡片內看見證據、限制條件、可執行連結與節省比較。
6. 在 60–90 秒 Demo 內清楚展示 AI 執行、資料可信度與實際生活價值。
7. 提供可選的 username／password 帳號，讓使用者保存清單、收藏與設定，不破壞匿名入口。

### 2.3 不變的產品原則

- **Constraints first**：硬限制先於價格排序。
- **Evidence before ranking**：關鍵欄位沒有證據，就不能進入主要排序。
- **Lowest cost, like-for-like**：只有在可比基準一致時，才能宣稱更便宜。
- **Free is conditional**：直接費用為零不代表無登記、無會員或無資格條件。
- **Narrow but honest**：固定圓山區、匿名可用並提供可選帳號，不假裝已覆蓋所有地區或即時庫存。
- **Actionable, not autonomous**：提供外部連結與下一步，不代替使用者完成付款或承諾結果。

## 3. 範圍與非範圍

### 3.1 MVP 包含

- 圓山區固定生活圈資料。
- Mobile-first responsive Web。
- 匿名使用；搜尋不要求登入，也提供 username／password 註冊、登入、登出與修改密碼。
- 語音輸入為主要入口；自然語言文字輸入為 fallback；結構化欄位只作為確認畫面的可編輯呈現。詳見 [SPEC-voice-input.md](./SPEC-voice-input.md)。
- 需求解析、限制摘要與可編輯確認。
- 第一階段篩選與兩個並行 Agent 的推薦排序狀態與結果。
- 五類 Dashboard 與每類 7–10 筆 Demo 資料。
- 事先匯入的人工整理資料與網路搜尋資料。
- 來源、證據摘錄、條件、搜尋／確認時間與資料狀態。
- 總成本、單位成本或份量比較。
- 在資料足夠時顯示在地常見方案、使用者原方案或 Costco 基準的節省比較；Costco 只有在使用者選擇可用時才納入。
- 建立清單、收藏、分享與回報問題的最小互動；清單、收藏與回報需要登入。
- 外部優惠／購買／報名連結。
- 已登入帳號保存清單、收藏與設定；匿名使用者可修改設定（只保留在目前瀏覽工作階段），收藏與清單需要登入。
- 使用者同意後取得目前位置，只用於該次搜尋的估算距離，不保存。

### 3.2 MVP 不包含

- 導航、路線規劃、Turn-by-turn directions、地圖路線引擎或即時交通導航。
- 健康、營養、醫療判斷、飲食建議或未查證營養推估。
- 即時庫存、即時名額或店家營業狀態的保證。
- 付款、下單、票券核銷或完整交易整合。
- 跨裝置需求歷史、完整個人檔案、精確位置保存。
- 執行期即時網路搜尋；資料匯入在搜尋前完成。
- 匿名工作階段資料合併到帳號。
- 全台地區覆蓋或任意地點搜尋。
- 以搜尋摘要、模型常識或猜測補出價格、資格、時間或營養資料。

## 4. BUILDMODE / 評審對齊

官方頁面將 Track 02「AI for Everyday Life」描述為改善人們生活、學習、溝通、購物、旅行、健康與日常生活導覽的 AI 產品，並列出 Consumer apps、Personal productivity、Wellness、Education、Lifestyle experiences 等方向。ALL in life 選擇其中的日常消費、生活體驗、資源取得與在地行動資訊，刻意將健康／營養與導航留到後續版本，避免在 Hackathon Demo 中做出沒有證據的承諾。

官方 FAQ 列出的評選面向包含 innovation、technical execution、product vision、real-world impact、user experience，以及適用時對 sponsor technologies 的運用。ALL in life 的對應證據如下：

- **Innovation**：將「限制解析 → 第一階段篩選（證據閘門 + 硬限制）→ 兩個並行 Agent 推薦排序（附理由）」組成一個日常決策流程，而不是只做聊天式搜尋。
- **Technical execution**：展示 deterministic 篩選、兩個 Agent 同時做推薦排序、來源與時間戳、缺欄位／衝突／逾時處理，以及 mobile-first UI。
- **Product vision**：先用一個固定生活圈完成可驗證閉環，再以相同資料契約擴展到其他地區與個人化需求。
- **Real-world impact**：讓預算有限、時間有限或不熟悉當地資源的人少做重複查找，並提高免費／公益資源的可見性。
- **User experience**：匿名可用、固定範圍、少量輸入、五類 Dashboard、卡片內直接看證據與下一步；註冊登入只在保存資料或共享功能時需要。
- **Sponsor technology**：官方 FAQ 表示非指定 sponsor challenge 時可自由選擇工具。若團隊實際使用 sponsor technology，需在 Demo 說明其位置與效果；沒有使用就不宣稱使用。

本產品的 Hackathon 主張應保持可驗證：**ALL in life 不承諾「找到全網最便宜」；它承諾在固定區域、明確限制與可讀證據範圍內，優先找出最低可比成本的選項。**

## 5. 目標使用者與核心情境

### 5.1 主要使用者

- 有明確預算上限的個人或小家庭。
- 臨時到圓山區、不了解當地選項的人。
- 想找低成本或免費資源，但願意遵守登記／資格條件的人。
- 願意在做決定前查看來源，不把 AI 回答當成官方保證的人。

### 5.2 Demo 情境 A：低預算付費選項

使用者輸入：「今天晚餐，2 人，總預算 NT$300，圓山區，可接受 20 分鐘或 2 公里內，想找可外帶選項。」

預期結果：

- 解析出日期、需求、2 人、NT$300、區域與距離／時間限制。
- 第一階段篩選只讓符合硬限制且有價格、份量／單位與來源的資料進入主要排序。
- 付費選項 Agent 對通過的食品與相關選項做推薦排序，每筆附理由。
- 顯示總成本、單位／份量、距離／時間文字、來源與證據。
- 在有可靠基準時顯示節省金額／比例；沒有基準時顯示「目前無足夠資料計算節省」，不虛構數字。

### 5.3 Demo 情境 B：免費／公益資源

使用者輸入：「這週末圓山區有沒有不用付費的活動或公共資源？可以先登記。」

預期結果：

- 免費資源 Agent 對通過篩選、直接費用為零的選項做推薦排序。
- 卡片清楚標示是否需登記、會員、資格、名額與時間。
- 點擊後可開啟官方或提供者頁面；不宣稱一定有名額。

### 5.4 Demo 情境 C：交通與生活活動比較

使用者指定可接受的時間／距離，查看交通費用或活動資訊。交通卡片只呈現來源提供的費用、服務時間、區域或距離／時間文字，不提供導航或路線指示。

## 6. Domain model 與詞彙表

### 6.1 核心詞彙

- **生活需求（Need）**：使用者想完成的事情，例如晚餐、採買、找活動或找免費資源。
- **硬限制（Hard constraint）**：不符合就不能推薦的條件，例如預算上限、人數、日期、區域、最大距離／時間或資格。
- **軟偏好（Soft preference）**：符合後用來排序或標籤的偏好，例如可外帶、品牌、時段或便利性。
- **生活選項（Option）**：一個可被使用者採取行動的食品、商品、資源、活動或交通服務。
- **候選紀錄（Candidate record）**：包含選項、比較欄位、來源與證據的結構化資料單位。
- **資料證據（Evidence）**：支持價格、費用、資格、時間、地點或可用性等關鍵欄位的來源片段、頁面或官方公告。
- **比較基準（Baseline）**：用來計算節省的已命名方案，例如使用者原方案、在地常見方案或使用者選擇可用的 Costco 基準。
- **推薦結果（Recommendation）**：通過硬限制與證據閘門後，依比較基準排序並呈現給使用者的候選紀錄。
- **直接成本（Direct cost）**：使用者為取得選項必須支付的價格，單位為新台幣（TWD）。
- **總可比成本（Comparable total cost）**：價格加上必要費用，扣除明確適用的折扣；不把未知費用當成零。
- **免費資源（Free resource）**：來源明確表示直接費用為零的選項；其他資格、登記、會員或押金條件仍須揭露。
- **資料狀態（Data status）**：已驗證、部分驗證／待確認、過期、衝突或無法納入比較。
- **固定區域（Fixed area）**：本 MVP 唯一展示範圍「圓山區」；不是使用者的精確住址。
- **第一階段篩選（Filter stage）**：對已匯入的候選紀錄套用證據閘門與硬限制的 deterministic 步驟；不是 Agent。
- **推薦排序（Recommendation ranking）**：Agent 對通過篩選的候選紀錄決定順序，不刪任何一筆，每筆附一句推薦理由；總可比成本第一、軟偏好其次。
- **Agent**：負責一種推薦排序任務的 LLM 執行單元；不上網搜尋。本產品只定義兩個並行 Agent。
- **估算距離（Estimated distance）**：使用者同意定位後，當下位置到選項地點的直線距離；只用於該次搜尋，不保存。
- 完整詞彙以 [CONTEXT.md](../CONTEXT.md) 為準。
- **使用者（User）**：使用 ALL in life 的人，可以是匿名使用者或已登入使用者。
- **帳號（Account）**：可用 username／password 登入，並保存帳號所屬清單、收藏與設定的持久身份。
- **工作階段（Session）**：一次匿名或已登入的瀏覽器使用期間；已登入 session 以 30 分鐘固定期限的 opaque token 識別。
- **支援式帳號恢復（Support-assisted account recovery）**：忘記密碼時只顯示平台支援 Email，不在 App 內自動重設 password。

### 6.2 五類生活選項

1. **食品**：餐食、食材、飲品或可比較的份量方案；重點欄位為價格、份量／人數、供應條件與來源。
2. **日用品**：日常用品、清潔用品或其他可購買物品；重點欄位為單價、包裝數量、最低購買條件與來源。
3. **免費／公益資源**：公共、社區、公益或免費服務；重點欄位為零費用證據、資格、登記、名額、時段與提供者。
4. **活動**：展覽、社區活動、講座或其他生活體驗；重點欄位為日期、時間、費用、登記與地點／區域。
5. **交通**：公共運輸、共享或其他移動選項；重點欄位為費用、服務時間、區域／距離文字與必要條件，不包含導航。

不同類別不直接用同一個單一分數混合排序。同一類別內付費選項與免費資源以「免費」標籤區分，不合成單一分數；沒有可比單位時只顯示總價，不假裝能做單位成本比較。

## 7. 使用流程與系統行為

### 7.1 端到端流程

1. 使用者在手機頁面按下錄音，說出需求、預算、份量／人數、可接受距離／時間與選填偏好；無法使用語音時改為輸入自然語言文字。
2. 系統將輸入解析為結構化需求，顯示「目前理解」摘要；使用者可修改，不需要帳號。
3. 使用者可選擇註冊／登入；匿名使用者直接繼續搜尋，已登入使用者的清單、收藏與設定保存到帳號。
4. 系統把需求與限制、設定（排除項目）以及使用者同意後的目前位置交給第一階段篩選。
5. 第一階段篩選對資料庫中已匯入的候選紀錄套用證據閘門與硬限制，產出通過清單、待確認清單與各限制的排除數。
6. 兩個 Agent **並行** 對通過清單做推薦排序；每個 Agent 內部按類別並行處理，某一類失敗只有該類退回總可比成本排序。
7. 每筆推薦結果附一句推薦理由；總可比成本是第一考量，軟偏好其次。
8. Dashboard 顯示五類結果。使用者可開啟卡片查看證據、外部連結、收藏、建立清單、分享或回報問題。

### 7.2 兩個並行 Agent

#### 付費選項 Agent

- 目的：對通過第一階段篩選、有直接成本的候選紀錄（食品、日用品、活動、交通）決定推薦順序。
- 輸入：需求與限制、通過篩選的候選紀錄摘要（id、名稱、總可比成本、單位／份量、估算距離、條件、標籤）。
- 輸出：依推薦順序排列的候選紀錄 id 與每筆一句推薦理由。
- 行為：不刪任何一筆、只能回傳輸入清單裡的 id；總可比成本第一、軟偏好其次；排在更便宜項目前面時理由必須說明原因。

#### 免費資源 Agent

- 目的：對通過第一階段篩選、直接費用為零的候選紀錄決定推薦順序。
- 輸入：同上，另含登記／會員／資格條件與時段。
- 輸出：同上。
- 行為：依需求符合度排序；非金錢條件仍顯示在卡片上。

兩個 Agent 不得互相等待。每個 Agent 內部按類別並行呼叫，某一類逾時或輸出不合格時，該類退回總可比成本排序並顯示原因。第一階段篩選與正規化是可測試的 deterministic processing，不是 Agent；資料匯入在搜尋之前完成，Agent 不上網。

## 8. 功能需求

### FR-01：固定區域與匿名／帳號入口

- 首頁明確顯示目前區域為「圓山區」。
- 匿名使用者不需要註冊或登入即可輸入需求、解析與搜尋。
- 提供 username／password 註冊、登入、登出與修改密碼。
- 不保存使用者的精確位置；匿名工作階段使用瀏覽器 `sessionStorage`，已登入工作階段使用固定 30 分鐘的 opaque session token。
- 登入 username 全站唯一、不分大小寫，允許英文字母、數字、`_`、`-`，長度 3–30 字元；nickname 是可修改的顯示名稱。
- password 最少 12 字元；伺服器只保存 Argon2id 或同等強度的 hash，不保存明文 password。
- 不使用 Cookie 保存 username、password 或 session token；token 存於 `sessionStorage`，重新整理同一分頁時可恢復登入。

### FR-02：最小輸入

語音輸入是主要入口：使用者說出需求，系統轉成逐字稿並解析為需求與限制。自然語言文字輸入是 fallback（麥克風不可用、辨識失敗或使用者選擇時）。表單不是獨立入口，只作為確認畫面的可編輯呈現。規則見 [SPEC-voice-input.md](./SPEC-voice-input.md)。最小結構化欄位為：

- 需求／品類；
- 任務預算；
- 使用人數／份量；
- 可接受距離／時間；
- 日期／時段；
- 選填偏好與必要資格。

若資訊不足，系統應指出缺少的欄位或以「待確認」呈現，不應默默猜測。

### FR-03：需求解析與確認

- 顯示解析後的需求、硬限制與軟偏好。
- 使用者可在送出搜尋前編輯解析結果。
- 金額、數量、日期、距離與時間必須保留原始單位並可辨識。

### FR-04：限制優先

- 預算上限、人數／份量、日期、固定區域、最大距離／時間與明確資格是硬限制。
- 任何不符合硬限制的紀錄不能進入主要推薦排序。
- 不得用較低價格抵銷硬限制不符合；例如便宜但份量不足的方案不得標成「最佳」。

### FR-05：並行搜尋

- 送出需求後，UI 先顯示第一階段篩選結果（通過數、待確認數），再顯示付費選項 Agent 與免費資源 Agent 各自的推薦排序狀態。
- 兩者應並行開始；一個 Agent 失敗時，另一個仍可完成並顯示部分結果。
- Agent 某一類別逾時或失敗時，該類別依總可比成本排序並顯示原因，不顯示假成功。

### FR-06：混合資料來源

- 支援人工整理（curated）與網路搜尋（web-searched）資料。
- 每筆資料要標示來源類型，不因是人工整理就省略來源或確認時間。
- Demo 使用的人工整理資料應是公開可核對的固定快照，不得填入虛構商家、價格或活動。

### FR-07：證據品質閘門

- 價格／費用、份量／單位、資格／登記、日期／時段、區域／距離等參與排序的關鍵欄位必須有可讀證據。
- 無法讀出關鍵資訊的紀錄可列在「待確認」，但不得進入主要排序或節省計算。
- 搜尋摘要、模型推測與沒有來源的常識不能單獨作為證據。

### FR-08：正規化與最低成本排序

- 金額統一以 TWD 顯示；必要費用要納入總可比成本。
- 有數量或份量時顯示單位成本；沒有可比份量時只顯示總價並標示限制。
- 同一需求先通過第一階段篩選，再由 Agent 推薦排序；推薦排序以總可比成本為第一考量、軟偏好其次，每筆附一句可見的推薦理由。
- 推薦排序失敗時，退回總可比成本由低至高，同價依資料新鮮度。
- 免費資源與付費選項不合成單一分數；同一類別中以「免費」標籤區分，生存模式開啟時免費排在最前。

### FR-09：五類 Dashboard

- 顯示且固定使用五個類別名稱：食品、日用品、免費／公益資源、活動、交通。
- Demo 資料集每類準備 7–10 筆通過證據閘門的可操作資料；畫面最多先顯示 10 筆。
- 若實際搜尋不足 7 筆，顯示實際數量與原因，不用假資料補滿。
- 每類顯示 Agent 來源與資料狀態，讓使用者知道結果是否來自人工整理、網路搜尋或兩者。

### FR-10：結果卡片

每張主要結果卡片至少包含：

- 名稱與提供者；
- 類別；
- 總成本與幣別；
- 單位成本或份量／人數（可取得時）；
- 距離／時間文字或服務時段（可取得時）；
- 估算距離（使用者同意定位時，標示「估算」）；
- 推薦理由；
- 必要限制條件；
- 來源類型、來源連結；
- 證據摘錄；
- 搜尋時間與確認時間；
- 資料狀態；
- 節省比較（有可靠基準時）；
- 一個可執行的外部動作，例如購買、報名、查看公告或聯絡提供者。

### FR-11：比較基準與節省

- 節省比較必須顯示基準名稱、基準價格、比較條件與資料時間。
- 可用基準包括使用者原方案、在地常見方案，或使用者明確選擇可用的 Costco 基準。
- 節省金額為基準總可比成本減去推薦總可比成本；比例分母為基準總可比成本。
- 若基準、價格、份量或必要費用不完整，顯示「無足夠資料計算節省」，不得虛構金額／比例。

### FR-12：清單、收藏、分享與回報

- 已登入使用者可將結果加入清單與收藏；匿名使用者點擊時提示登入。
- 匿名使用者的設定只在目前瀏覽工作階段有效；登入後以帳號資料為準，不合併匿名資料。
- 分享內容應包含需求摘要、結果名稱、來源與資料時間；不包含精確位置或不必要個資。
- 已登入使用者可提交回報：資料回報（價格過期、條件錯誤、來源失效、分類錯誤）或體驗回報（食安、過敏、身體不適）。回報是共享資料，不自動改變資料狀態；體驗回報標示「使用者回報，非系統判斷」。

### FR-13：例外與空結果

- 沒有符合硬限制的結果時，說明是哪個限制造成空結果，並讓使用者選擇放寬限制。
- 來源衝突時顯示衝突，採較新且較權威來源；無法判定時排除排序。
- 過期資料仍可作為線索，但要標示過期，不能冒充目前可用。
- 單一 Agent 失敗時保留另一 Agent 的結果與狀態。

### FR-14：明確排除導航與健康判斷

- 交通結果不得提供導航按鈕、路線規劃或轉向指示。
- 食品結果不得推導健康分數、營養建議、醫療建議或未查證營養數值。
- UI、Demo 腳本與文案不可暗示上述功能已完成。

### FR-15：可選帳號與登入

- 匿名使用者可完成需求解析與搜尋；登入不是搜尋前置條件。
- 註冊需要全站唯一、不分大小寫的 username、至少 12 字元的 password，以及可選 nickname；nickname 預設等於 username，之後可修改。
- 登入、登出與修改密碼使用 Auth API；忘記密碼按鈕只顯示 `SUPPORT_EMAIL=xuanweilin805@gmail.com`，不提供 App 內自動 reset。
- Server 只保存 password hash；Browser 不保存 username／password。登入成功後只將隨機 opaque session token 保存到 `sessionStorage`。
- session token 建立後固定 30 分鐘到期，不因請求自動延長；登出立即撤銷 token。
- 已登入帳號保存清單、收藏與設定；音檔、逐字稿、需求與限制、搜尋歷史不保存到帳號資料。
- 不合併匿名資料：登入後帳號資料取代目前工作階段的設定；匿名使用者沒有清單與收藏。
- 回報是共享資料，需要登入。揪團是純顯示（商家兌換碼與成團後成本試算），沒有成員關係，不是共享資料。

## 9. 資料與證據規則

### 9.1 候選紀錄最小資料契約

每筆資料至少應能表達以下欄位；實際 table 定義見 SPEC-backend.md §6，欄位的蒐集與可空規則見 SPEC-ingestion.md §4：

```text
id
category
agent                    # paid | free，由匯入者依來源判定
title
provider
price_total_twd          # null = 未知，不當 0
price_unit
quantity_or_servings
mandatory_fees_twd
discount_twd
eligibility
registration_required
availability_or_event_time
valid_until              # 來源明示的有效期限；null = 未明示。過期的紀錄退出主要排序並標示到期時間
address                  # 選項地址，來源原文；沒有就 null
lat, lng                 # 選項地點座標，由 geocoding 產生；沒有就 null，該筆不做距離篩選
distance_or_time_text    # 來源原文
tags                     # 排除項目用的成分標籤；null = 未標示
source_url
source_type              # curated | web-searched
source_authority         # official | provider | public | other
evidence                 # 逐欄證據摘錄陣列：{field, quote, url, checked_at}
collected_at
verified_at
data_status
action_url
baseline                 # 比較基準（可為 null）
group_offer              # 團體優惠：人數條件、折扣、兌換碼（可為 null）
```

免費資源可將 `price_total_twd` 設為 0，但只有在來源明確表示無直接費用時才可如此設定；登記、會員、資格、押金、材料費或名額條件仍要放在 `eligibility` 或對應欄位。

### 9.2 來源與證據優先順序

1. 官方公告、官方活動頁或提供者正式頁面。
2. 公共機關、場館、社區或公益組織的正式資訊。
3. 可辨識提供者且有日期的可靠公開頁面。
4. 搜尋結果只作為找線索；不能取代原始頁面中的關鍵證據。

每筆結果都要顯示來源 URL、來源類型、證據摘錄、`collected_at` 與 `verified_at`。若頁面沒有可讀關鍵欄位，狀態設為「部分驗證／待確認」或「無法納入比較」。

### 9.3 價格與比較規則

- `總可比成本 = 商品／服務價格 + 必要費用 - 明確適用折扣`。
- 不把未知運費、服務費、押金或會員費當作 0。
- 優惠只有在使用者符合來源列出的條件時才可套用。
- 不同份量、人數、包裝或服務內容不得直接宣稱誰比較便宜。
- 單位成本要說明單位，例如每人、每份、每公升或每件。
- 「最低成本」指在本次搜尋範圍、已知來源與已套用限制內最低，不代表全網保證最低。

### 9.4 時間、距離與可用性

- 同時記錄頁面／公告上的有效時間（若有）與系統搜尋／確認時間。
- 距離／時間若由來源提供，保留來源原文；系統估算距離為使用者當下位置到選項地點的直線距離，必須標示「估算」。
- 只在使用者同意後取得目前位置，且只用於該次搜尋，不保存、不寫 log；不在 MVP 產生路線。
- 不承諾即時庫存、即時名額、營業狀態或交通即時到站。

### 9.5 衝突、過期與缺欄位

- **來源不同就是不同的候選紀錄**：同一個選項在兩個來源價格或時間不同時，兩筆都建、都列出、各自帶自己的來源與證據摘錄，由使用者判斷；系統不做跨來源的合併或取捨。見 ADR 0002 與 SPEC-ingestion.md §6.1。
- 同一來源以較新且仍在有效期的內容為準；同一來源自己前後矛盾時顯示「衝突待確認」，不進主要排序。
- 價格、日期、資格或費用缺失時，不推導或補值。
- 來源超過其明示有效期，或無法確認仍有效時，標示「過期／待確認」。

### 9.6 授權與資料責任

- 只使用團隊有權使用的公開資料、人工整理內容與可核對來源。
- 儲存必要的結構化欄位與短證據摘錄，不大量複製來源頁面。
- 外部連結回到原始提供者，並在 UI 提醒使用者以原始頁面為準。
- 任何供應商、活動主辦者或公共機構的名稱與價格都必須能追溯。

### 9.7 帳號與工作階段資料契約

Database 為本機 PostgreSQL；完整 schema 見 SPEC-backend.md §6。Logical schema：

```text
users
  id
  username                 # normalized unique
  password_hash            # Argon2id or equivalent; never plaintext
  nickname
  created_at
  updated_at

auth_sessions
  id
  user_id
  token_hash               # never store the raw browser token
  created_at
  expires_at               # created_at + 30 minutes
  revoked_at

account_data               # 每個帳號一列
  user_id
  list                     # 候選紀錄 id 陣列
  favs
  settings                 # 每月預算、已花費、生存模式、排除項目、偏好、Costco 基準是否可用
  profile

candidates                 # 事先匯入的候選紀錄、來源與證據
reports                    # 共享回報：candidate_id、user_id、reason、note、created_at
```

- `account_data` 是帳號私有資料。
- `reports` 是共享資料；必須可追溯提交者與時間。
- 音檔、逐字稿、需求與限制、搜尋歷史與使用者位置不進 Database。
- 揪團沒有資料表；團體優惠與兌換碼是候選紀錄的欄位。

## 10. 非功能需求

### NFR-01：Mobile-first

- 先以手機直向版面設計；支援至少 320px 寬度的現代瀏覽器。
- 主要流程不依賴 hover；卡片、證據抽屜與外部動作適合觸控。
- 內容在桌面寬度仍可閱讀，但不是優先驗收目標。

### NFR-02：可感知效能

- 使用者送出後立即看到兩個 Agent 的進度，不顯示空白等待頁。
- 準備好的 Demo 環境以 15 秒內呈現第一批可用結果為目標。
- 任一 Agent 超時時先呈現另一 Agent 或固定整理資料；不可無限等待。

### NFR-03：可理解與可及性

- 使用清楚的繁體中文，必要時保留 English technical terms。
- 重要狀態不只靠顏色表達；使用標籤、圖示替代文字或明確文案。
- 主要文字、來源、價格與限制在手機上不需水平捲動即可閱讀。
- 互動元件具可辨識 focus、足夠觸控尺寸與語意化標題。

### NFR-04：透明與可追溯

- 使用者可從推薦卡片一路查看來源、證據與時間。
- AI 解析、搜尋結果、正規化與排序狀態要能由團隊在 Demo 中解釋。
- UI 不將「已找到」寫成「官方保證」或「即時保證」。

### NFR-05：隱私與安全

- 不儲存精確地址、GPS、電話或付款資料；目前位置只在使用者同意後用於該次搜尋，不保存；帳號只保存必要的 username、password hash、nickname 與帳號功能資料。
- 預設不保存自然語言輸入原文；若為錯誤排查需暫存，應去除個資並設定短保留期。
- 不保存明文 password；不把 password 寫入 Cookie、`sessionStorage`、log 或 Email。
- session token 只放在 `sessionStorage`，不使用 Cookie；token 固定 30 分鐘到期，登出時撤銷。
- Auth API 必須使用 HTTPS；正式環境使用嚴格 CSP、輸出編碼與最少化第三方 script，降低 XSS 竊取 token 的風險。
- 忘記密碼只顯示 `SUPPORT_EMAIL`，支援人員不得要求使用者傳送明文 password。
- 外部連結應清楚標示離開 ALL in life，並避免未經確認的自動操作。

### NFR-06：成本與退化

- 對網路搜尋設定來源、查詢數與時間上限，避免無限制 API 成本。
- 使用固定整理資料作為 Demo fallback，但仍保留證據與確認時間。
- 任何 partial result 都標示完成度與失敗原因，不用模型生成內容掩蓋資料缺口。

## 11. 驗收條件（Definition of Done）

以下條件全部達成，才算 MVP Demo ready：

1. **產品識別**：頁面、Demo 與文件只使用產品名稱「ALL in life」，並明確顯示固定區域「圓山區」。
2. **匿名與帳號入口**：手機瀏覽器可直接匿名使用；也能以 username／password 註冊、登入、登出與修改密碼，不保存敏感位置資料。
3. **輸入可控**：語音與文字 fallback 至少能表達需求、預算、人數／份量、距離／時間與日期；送出前看得到逐字稿與解析摘要並可修正。語音驗收案例見 SPEC-voice-input.md §9。
4. **兩 Agent 並行**：畫面能看到第一階段篩選結果，以及付費選項 Agent 與免費資源 Agent 同時做推薦排序，且任一失敗不會讓另一個結果消失。
5. **五類結果**：Dashboard 有食品、日用品、免費／公益資源、活動、交通五類；Demo 固定資料集中每類有 7–10 筆通過證據閘門的可操作紀錄。
6. **限制先行**：給定預算、份量／人數、日期、區域與距離／時間後，不符合硬限制的候選不進主要排序。
7. **最低可比成本**：付費結果的推薦排序以可比總成本為第一考量，每筆附推薦理由，並能解釋總價、單位／份量與必要費用；未知費用不當作零；推薦排序失敗時退回成本排序。
8. **證據可見**：每個主要結果都有來源、證據摘錄、來源類型、搜尋／確認時間、資料狀態與外部動作。
9. **節省可驗證**：至少一個 Demo 情境能以已知基準顯示節省金額／比例；基準不足時 UI 明確顯示無法計算，而非補數字。
10. **免費資源可行動**：至少一筆免費／公益資源明確顯示直接費用為零、登記／資格／時段條件、來源與下一步連結。
11. **例外透明**：能示範或至少在測試資料中處理缺欄位、來源衝突、過期、Agent 逾時與無結果。
12. **範圍守門**：Demo 中沒有導航、路線規劃、健康／營養／醫療建議、即時庫存保證或虛構來源。
13. **帳號安全**：password 只以 hash 保存；session token 只在 `sessionStorage` 保存 30 分鐘；登出會撤銷 token；忘記密碼只顯示支援 Email。

### 驗收用最小測試案例

- **Case A：預算與人數**
  - Given：2 人、NT$300 上限、圓山區、20 分鐘／2 公里內。
  - When：查找食品。
  - Then：只出現符合限制且有價格與份量證據的結果；排序可由成本解釋。

- **Case B：免費但有條件**
  - Given：週末、直接費用為零、可接受先登記。
  - When：查找活動或公益資源。
  - Then：至少一筆卡片清楚區分「免費」與登記／資格／名額條件。

- **Case C：缺少基準**
  - Given：結果有價格，但沒有同份量的原方案或常見方案。
  - When：查看節省。
  - Then：顯示無足夠資料計算，不顯示推測比例。

- **Case D：來源不同**
  - Given：同一家提供者的兩個來源，費用或時間不同。
  - When：查看結果。
  - Then：兩筆都出現在結果中，各自顯示自己的來源、來源類型與證據摘錄；同一來源自己前後矛盾的那筆標為「衝突待確認」並排除主要排序。

- **Case Auth-A：註冊與登入**
  - Given：使用者輸入合法且唯一的 username、12 字元以上 password，可選 nickname。
  - When：註冊後重新整理同一分頁。
  - Then：帳號建立成功，password 只存 hash，session token 在 `sessionStorage`，`/api/auth/me` 恢復登入。

- **Case Auth-B：session expiry**
  - Given：session token 建立已超過 30 分鐘。
  - When：使用者呼叫受保護功能。
  - Then：回傳 401、清除 token、回到匿名狀態並提示重新登入。

- **Case Auth-C：匿名不合併**
  - Given：匿名 session 改過設定，使用者登入既有帳號。
  - Then：帳號資料取代目前工作階段的設定；匿名沒有清單／收藏可遷移；音檔、逐字稿、需求與限制不遷移。
  - Given：匿名使用者點擊 ★ 或加入清單。
  - Then：提示登入，不寫入任何資料。

- **Case Auth-D：忘記密碼**
  - Given：使用者點擊忘記密碼。
  - Then：只顯示 `xuanweilin805@gmail.com`，不在 App 內自動重設，也不要求寄送明文 password。

## 12. 風險與應對

- **資料過期**：價格、名額與活動資訊可能改變。每筆顯示時間，使用固定快照作 Demo fallback，不承諾即時狀態。
- **價格不可比**：包裝、份量、會員價或必要費用不同。顯示比較單位與條件；不可比就不做節省計算。
- **語音辨識錯誤**：逐字稿可能聽錯數字或人數。確認畫面永遠顯示逐字稿原文與解析欄位，使用者可在搜尋前用點擊或修正語句更正；不自動送出。
- **推薦排序幻覺**：模型可能補出不存在的店家或價格。Agent 只能回傳輸入清單裡的候選紀錄 id，伺服器驗證並補回遺漏；所有主要欄位必須有來源證據，無證據不排序。
- **免費資源誤解**：免費可能仍需登記、資格、會員、押金或材料費。把條件放在卡片前段，不只顯示醒目的「免費」。
- **來源授權問題**：網頁內容未必可任意複製。只保存必要欄位與短摘錄，保留原始連結並確認使用條款。
- **Agent 延遲／API 成本**：資料事先匯入、每個 Agent 按類別並行、每類設 timeout、失敗退回成本排序。
- **圓山區範圍模糊**：Demo 先固定團隊定義的生活圈與邊界文字，資料集中的 `area` 必須一致；不暗示全台適用。
- **匿名無收藏**：★ 與清單按鈕在匿名時提示登入，不讓使用者以為資料已保存。
- **session token 外洩**：`sessionStorage` 可被同源 JavaScript 讀取；使用 HTTPS、嚴格 CSP、輸出編碼、短期限 token 與撤銷機制降低風險，不把 password 存到瀏覽器。
- **帳號恢復不足**：忘記密碼只提供支援 Email；支援流程不得要求明文 password，人工身份驗證與重設作業屬平台營運責任。
- **帳號資料取代**：登入後帳號資料取代工作階段設定，UI 明示；不遷移語音與需求原文。
- **範圍膨脹**：健康、營養、導航、交易與更多地區列入 backlog；Demo 只驗收本 PRD 的閉環。

## 13. 60–90 秒 Demo 故事線

### 0–10 秒：提出問題

「在圓山區臨時要解決一個日常需求，使用者通常要分別查價格、份量、活動條件與免費資源，還要自己判斷哪些資訊可信。ALL in life 把這些限制放進同一個決策流程。」

### 10–20 秒：輸入需求

按下錄音，說出：「今天晚餐兩個人預算三百圓山區二十分鐘內可外帶。」畫面先顯示逐字稿，再顯示解析後的預算、人數、區域與限制，快速確認後送出。

### 20–35 秒：展示兩個並行 Agent

先顯示第一階段篩選結果（幾筆通過、幾筆待確認、哪個限制排除了幾筆），再同時展示：

- 付費選項 Agent：對通過篩選的付費選項做推薦排序，每筆附理由；
- 免費資源 Agent：對直接費用為零但可能需要登記或資格的資源做推薦排序。

強調資料已先通過證據閘門與硬限制，兩個 Agent 並行，只決定順序、不造資料。

### 35–52 秒：展示五類 Dashboard

快速滑過食品、日用品、免費／公益資源、活動、交通五個類別。指出每類有 7–10 筆資料、每筆標示來源類型與資料狀態；不要花時間逐張讀完。

### 52–68 秒：打開結果與證據

點開一張食品或日用品卡片，展示總成本、單位／份量、必要條件、來源 URL、證據摘錄、確認時間與外部動作。指出「便宜」是通過限制與可比欄位後才成立。

### 68–80 秒：展示節省

切換到有可靠基準的結果，展示節省金額／比例與基準名稱。若示範資料沒有足夠基準，反而展示「無足夠資料計算」來證明產品不虛構數字。

### 80–90 秒：展示免費資源與邊界

打開一筆免費／公益資源，指出直接費用為零，但登記／資格／時段仍清楚可見。收尾說明：這版不做導航、不做健康／營養判斷、不保證即時庫存；下一步是擴大資料與驗證能力。

## 14. Hackathon 團隊執行順序

1. **先凍結資料契約**：確認五類欄位、狀態值、證據格式、比較基準與 Auth logical schema。
2. **先做 Auth 基礎**：建立 users／auth_sessions／account_data，完成 username/password hash、30 分鐘 token 與支援 Email。
3. **先做可信資料**：每類匯入 7–10 筆可核對紀錄到 candidates，標示 curated／web-searched、來源、證據、時間與座標。
4. **接輸入與解析**：自然語言與表單共用同一個結構化需求。
5. **做第一階段篩選**：證據閘門 + 硬限制 + 各限制排除數；將無證據、衝突與過期資料隔離到待確認。
6. **接兩個並行 Agent**：按類別並行推薦排序，先讓狀態、timeout、partial result 與成本排序 fallback 可展示。
7. **完成手機 Dashboard**：五類、結果卡、證據抽屜、外部動作、帳號入口與錯誤狀態。
8. **跑驗收案例與 Demo 排練**：用固定輸入重播，確認 Auth 與每個數字都能回到來源，並在 90 秒內完成故事線。

## 15. 後續路線圖

### Phase 1：Demo 後的可靠性

- 自動來源刷新與過期偵測。
- 更完整的衝突比對與資料品質儀表板。
- 更多圓山區資料與實際使用者回報流程。
- 可解釋的排序偏好與更好的部分結果處理。

### Phase 2：擴大生活圈與個人化

- 使用者明確同意後的地區選擇與位置權限。
- 更多行政區與跨區比較。
- 跨區個人化需求、常用份量、會員資格與更完整的帳號檔案。
- 更完整的商家、活動主辦者與公共資源合作資料。

### Phase 3：延後能力

- 健康／營養資訊：需可靠資料、清楚免責與專業審核，不從 MVP 的食品價格資料直接推導。
- 導航與路線：需位置權限、地圖／交通資料、即時狀態與新的隱私設計。
- 交易整合：付款、下單、票券與庫存需與提供者正式整合。
- 即時價格、名額與庫存：需來源 API 或持續驗證機制。

## 16. 最終成功定義

ALL in life 的 MVP 不以「功能最多」或「涵蓋所有生活」成功，而以以下閉環成功：

> 一位匿名或已登入使用者在圓山區輸入一個有預算與限制的日常需求，看到兩個 Agent 並行搜尋，從五類結果中找到有證據的可行選項，理解為何它符合限制、能否省下明確金額，以及下一步該查看哪個原始來源；已登入者可保存清單、收藏與設定。

只要這個閉環可在手機上穩定重播、資料不造假、限制與證據可解釋，ALL in life 就具備可供評審理解、團隊開發與後續擴展的 Hackathon MVP。
