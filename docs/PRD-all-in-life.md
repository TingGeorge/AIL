# ALL IN LIFE — Product Requirements Document（PRD）

- 文件狀態：Hackathon MVP product baseline
- 版本：v0.3
- 日期：2026-09-06
- 產品名稱：**ALL IN LIFE**
- Pilot area：**圓山區**
- 平台：Mobile-first responsive Web
- 使用方式：匿名可直接使用；選擇登入後可保存與跨裝置同步
- 對齊活動：BUILDMODE 2026，Track 02「AI for Everyday Life」
- 對齊來源：[FUTUREMODE BUILDMODE Hackathon 官方頁面](https://www.futuremode.xyz/hackathon)（2026-09-04 查閱）

> **實作對齊：** 目前 `mvp/` 不讓 AI 在使用者 request 當下自行上網找商家。AI 只把需求轉成 strict `SearchConstraints`，並從伺服器允許的事實代碼中選推薦理由；D1／snapshot、硬限制、Evidence Gate 與 CP engine 才決定候選及排序。付費與零元「獵人」保留為產品敘事與候選分流，不是兩個可創造事實的自治 Agent。

## 1. 一頁摘要

ALL IN LIFE 協助使用者在固定的圓山區生活圈內，依照預算、份量／人數、距離／時間與其他限制，快速找到可執行的生活選項。系統的核心不是把網路內容重新摘要，而是先套用硬限制，再以可比的成本排序，並讓每個結論都能回到來源與證據。

MVP 以兩條受控候選路徑查詢已匯入資料：

1. **付費選項路徑**：查食品、日用品、活動與交通等有直接支出的選項，並在條件符合後比較可證明的總成本。
2. **免費資源路徑**：查直接費用為零的公共、公益或社區資源；同時揭露登記、會員、資格、時段等非金錢條件。

兩條路徑的結果經過資料正規化與證據品質閘門後，進入五類橫向分類結果：

- 食品
- 日用品
- 免費／公益資源
- 活動
- 交通

每類在 Demo 資料集準備 7–10 筆可操作資料。資料可以來自人工整理與網路搜尋的混合來源，但不得以沒有可讀證據的資料參與推薦排序。MVP 的主要成果是證明「同一個需求可以節省明確金額／比例」以及「至少找到一筆條件清楚的免費／公益資源」。

## 2. 問題、目標與產品原則

### 2.1 使用者問題

日常決策常同時受到預算、份量、人數、地點、時間與資格條件限制。資訊分散在商家頁面、活動頁面、公共資源公告與搜尋結果中，使用者需要自己確認：

- 價格是否真的可比；
- 份量或使用人數是否相同；
- 「免費」是否仍需要登記、會員或資格；
- 資訊是否過期；
- 推薦是否真的符合原本的距離與時間限制。

### 2.2 MVP 目標

1. 讓使用者用自然語言或最小表單說明需求與限制。
2. 以同一份結構化需求查詢付費選項與免費資源；AI 只協助解析與說明。
3. **先篩硬限制，再以最低可比成本排序**；不因未知欄位而把資料當成便宜選項。
4. 以五類橫向分類呈現有來源、有時間戳、有條件的結果；數量依真實資料 coverage 顯示。
5. 讓使用者在結果卡片內看見證據、限制條件、可執行連結與節省比較。
6. 在 60–90 秒 Demo 內清楚展示 AI 執行、資料可信度與實際生活價值。

### 2.3 不變的產品原則

- **Constraints first**：硬限制先於價格排序。
- **Evidence before ranking**：關鍵欄位沒有證據，就不能進入主要排序。
- **Lowest cost, like-for-like**：只有在可比基準一致時，才能宣稱更便宜。
- **Free is conditional**：直接費用為零不代表無登記、無會員或無資格條件。
- **Narrow but honest**：固定圓山區、匿名可用，不假裝已覆蓋所有地區或即時庫存。
- **Actionable, not autonomous**：提供外部連結與下一步，不代替使用者完成付款或承諾結果。

## 3. 範圍與非範圍

### 3.1 MVP 包含

- 圓山區固定生活圈資料。
- Mobile-first responsive Web。
- 匿名可直接使用；可選擇登入以保存個人檔案、偏好、清單與歷史。
- 自然語言輸入與結構化欄位輸入。
- 需求解析、限制摘要與可編輯確認。
- 付費與零元候選的搜尋狀態與結果。
- 五類橫向分類與獨立的 Demo 固定情境。
- 混合人工整理資料與網路搜尋資料。
- 來源、證據摘錄、條件、搜尋／確認時間與資料狀態。
- 總成本、單位成本或份量比較。
- 在資料足夠時顯示在地常見方案、使用者原方案或 Costco 基準的節省比較；Costco 只有在使用者選擇可用時才納入。
- 建立清單、收藏、分享與回報資料問題的最小互動。
- 外部優惠／購買／報名連結。

### 3.2 MVP 不包含

- 導航、路線規劃、Turn-by-turn directions、地圖路線引擎或即時交通導航。
- 健康、營養、醫療判斷、飲食建議或未查證營養推估。
- 即時庫存、即時名額或店家營業狀態的保證。
- 付款、下單、票券核銷或完整交易整合。
- 第三方 SSO、離線衝突合併與精確位置保存；本版已有生活帳號驗證與 D1 個人狀態持久化。
- 全台地區覆蓋或任意地點搜尋。
- 以搜尋摘要、模型常識或猜測補出價格、資格、時間或營養資料。

### 3.3 產品 SOP 與畫面流程（v0.2）

1. **進入方式**：首次開啟可選匿名、生活帳號或 Demo。匿名模式不阻擋核心功能；登入模式由 D1 保存清單、預算、收藏與歷史，Demo 固定情境與正式帳號資料分離。
2. **首次設定**：依序設定匿名暱稱與頭像、單次預算與人數、硬性排除與軟偏好；所有項目之後都能在設定中修改。
3. **提出需求**：首頁把語音按鈕置於「開始探索」之前，文字對話框可直接編輯；兩種輸入都寫入同一份結構化需求。
4. **確認限制**：搜尋前可編輯需求、日期、時段、類別、預算、人數、最大距離、硬性排除與軟偏好。硬限制會排除，偏好只調整排序。
5. **搜尋回饋**：前端計時器逐步呈現來源整理、營業時間、限制、總成本與證據檢查，避免等待時沒有回饋；此進度不冒充真實後端百分比。
6. **比較結果**：餐飲、日用、育樂、交通共用一致卡片，顯示距離、時間、服務方式、總成本、人均、節省、CP 值、來源與查核日期。
7. **採取行動**：詳情頁可收藏、加入清單、標記已買、移除、分享、開啟地圖或回報資料；通知頁集中顯示收藏到期與成團狀態。
8. **揪團**：清楚列出品項與店家、單獨／成團人均、門檻、目前人數及節省；使用者可分享邀請，未達門檻前取消。
9. **回顧**：設定頁可進入個人檔案、歷史與消費分析，查看月預算、已花、剩餘、類別占比和累積節省。

UX 原則是「一次只做一個主要決定、重要資訊就地呈現、進階條件再展開」。通知不與清單混在同一頁；個人資料、預算及偏好集中在設定；結果頁負責比較，詳情頁負責證據與行動，以減少重複入口和過長捲動。

## 4. BUILDMODE / 評審對齊

官方頁面將 Track 02「AI for Everyday Life」描述為改善人們生活、學習、溝通、購物、旅行、健康與日常生活導覽的 AI 產品，並列出 Consumer apps、Personal productivity、Wellness、Education、Lifestyle experiences 等方向。ALL in life 選擇其中的日常消費、生活體驗、資源取得與在地行動資訊，刻意將健康／營養與導航留到後續版本，避免在 Hackathon Demo 中做出沒有證據的承諾。

官方 FAQ 列出的評選面向包含 innovation、technical execution、product vision、real-world impact、user experience，以及適用時對 sponsor technologies 的運用。ALL in life 的對應證據如下：

- **Innovation**：將「限制解析 → 兩個並行搜尋 → 證據閘門 → 可比成本排序」組成一個日常決策流程，而不是只做聊天式搜尋。
- **Technical execution**：展示 AI 需求解析、兩條資料路徑、資料正規化、來源與時間戳、缺欄位／衝突／逾時處理，以及 mobile-first UI。
- **Product vision**：先用一個固定生活圈完成可驗證閉環，再以相同資料契約擴展到其他地區與個人化需求。
- **Real-world impact**：讓預算有限、時間有限或不熟悉當地資源的人少做重複查找，並提高免費／公益資源的可見性。
- **User experience**：匿名、固定範圍、少量輸入、五類橫向分類、卡片內直接看證據與下一步；不要求使用者先註冊。
- **Sponsor technology**：官方 FAQ 表示非指定 sponsor challenge 時可自由選擇工具。若團隊實際使用 sponsor technology，需在 Demo 說明其位置與效果；沒有使用就不宣稱使用。

本產品的 Hackathon 主張應保持可驗證：**ALL in life 不承諾「找到全網最便宜」；它承諾在固定區域、明確限制與可讀證據範圍內，優先找出最低可比成本的選項。**

## 5. 目標使用者與核心情境

### 5.1 主要使用者

- 有明確預算上限的個人或小家庭。
- 臨時到圓山區、不了解當地選項的人。
- 想找低成本或免費資源，但願意遵守登記／資格條件的人。
- 願意在做決定前查看來源，不把 AI 回答當成官方保證的人。

### 5.2 Demo 情境 A：低預算付費選項

使用者輸入：「今天晚餐，2 人，總預算 NT$300，圓山區，可接受 20 分鐘或 2 公里內，想找可外帶選項。」

預期結果：

- 解析出日期、需求、2 人、NT$300、區域與距離／時間限制。
- 付費選項搜尋 Agent 找到食品與相關選項。
- 只有符合硬限制且有價格、份量／單位與來源的資料進入主要排序。
- 顯示總成本、單位／份量、距離／時間文字、來源與證據。
- 在有可靠基準時顯示節省金額／比例；沒有基準時顯示「目前無足夠資料計算節省」，不虛構數字。

### 5.3 Demo 情境 B：免費／公益資源

使用者輸入：「這週末圓山區有沒有不用付費的活動或公共資源？可以先登記。」

預期結果：

- 免費資源搜尋 Agent 找到直接費用為零的選項。
- 卡片清楚標示是否需登記、會員、資格、名額與時間。
- 點擊後可開啟官方或提供者頁面；不宣稱一定有名額。

### 5.4 Demo 情境 C：交通與生活活動比較

使用者指定可接受的時間／距離，查看交通費用或活動資訊。交通卡片只呈現來源提供的費用、服務時間、區域或距離／時間文字，不提供導航或路線指示。

## 6. Domain model 與詞彙表

### 6.1 核心詞彙

- **生活需求（Need）**：使用者想完成的事情，例如晚餐、採買、找活動或找免費資源。
- **硬限制（Hard constraint）**：不符合就不能推薦的條件，例如預算上限、人數、日期、區域、最大距離／時間或資格。
- **軟偏好（Soft preference）**：符合後用來排序或標籤的偏好，例如可外帶、品牌、時段或便利性。
- **生活選項（Option）**：一個可被使用者採取行動的食品、商品、資源、活動或交通服務。
- **候選紀錄（Candidate record）**：包含選項、比較欄位、來源與證據的結構化資料單位。
- **資料證據（Evidence）**：支持價格、費用、資格、時間、地點或可用性等關鍵欄位的來源片段、頁面或官方公告。
- **比較基準（Baseline）**：用來計算節省的已命名方案，例如使用者原方案、在地常見方案或使用者選擇可用的 Costco 基準。
- **推薦結果（Recommendation）**：通過硬限制與證據閘門後，依比較基準排序並呈現給使用者的候選紀錄。
- **直接成本（Direct cost）**：使用者為取得選項必須支付的價格，單位為新台幣（TWD）。
- **總可比成本（Comparable total cost）**：價格加上必要費用，扣除明確適用的折扣；不把未知費用當成零。
- **免費資源（Free resource）**：來源明確表示直接費用為零的選項；其他資格、登記、會員或押金條件仍須揭露。
- **資料狀態（Data status）**：已驗證、部分驗證／待確認、過期、衝突或無法納入比較。
- **固定區域（Fixed area）**：本 MVP 唯一展示範圍「圓山區」；不是使用者的精確住址。
- **獵人／候選路徑**：付費與零元資料的產品分流；AI 不直接搜尋網路或創造候選事實。

### 6.2 五類生活選項

1. **食品**：餐食、食材、飲品或可比較的份量方案；重點欄位為價格、份量／人數、供應條件與來源。
2. **日用品**：日常用品、清潔用品或其他可購買物品；重點欄位為單價、包裝數量、最低購買條件與來源。
3. **免費／公益資源**：公共、社區、公益或免費服務；重點欄位為零費用證據、資格、登記、名額、時段與提供者。
4. **活動**：展覽、社區活動、講座或其他生活體驗；重點欄位為日期、時間、費用、登記與地點／區域。
5. **交通**：公共運輸、共享或其他移動選項；重點欄位為費用、服務時間、區域／距離文字與必要條件，不包含導航。

不同類別不直接用同一個單一分數混合排序。付費選項與免費資源分開標示；沒有可比單位時只顯示總價，不假裝能做單位成本比較。

## 7. 使用流程與系統行為

### 7.1 端到端流程

1. 使用者在手機頁面選擇「快速填寫」或「直接說」。快速填寫包含需求、任務預算、份量／人數、可接受距離／時間與選填偏好；直接說支援文字與語音，語音先轉成可編輯逐字稿。
2. 系統將表單、文字或語音逐字稿解析為同一份結構化需求，顯示「目前理解」摘要；使用者可逐欄修改，不需要帳號。系統不得把辨識不清或沒有說明的限制自動猜成已確認條件。
3. 系統將圓山生活圈、需求與限制交給伺服器驗證後的 catalog 查詢。
4. 付費與零元兩條路徑查詢各自類別，回傳候選紀錄與逐欄證據。
5. 正規化流程統一價格、單位、日期、區域、資格與資料狀態；品質閘門移除關鍵欄位無證據的資料。
6. 先套用硬限制，再依可比成本與透明的次要條件排序。
7. 橫向分類列顯示五類結果。使用者可開啟卡片查看證據、外部連結、收藏、建立清單、分享或回報問題。

### 7.2 兩條受控候選路徑

#### 付費選項搜尋 Agent

- 目的：在食品、日用品、活動、交通及其他明確有直接成本的選項中找出符合條件者。
- 輸入：需求、預算、人數／份量、日期、固定區域、距離／時間限制與偏好。
- 輸出：選項名稱、提供者、總價、單位／份量、必要費用、適用條件、區域／距離文字、來源、證據與時間戳。
- 行為：先排除超出硬限制或無法讀出關鍵價格／條件的結果，再依最低可比成本排序。

#### 免費資源搜尋 Agent

- 目的：尋找直接費用明確為零的資源，不把「可能免費」當成已確認免費。
- 輸入：需求、日期、固定區域、可接受距離／時間、資格與登記偏好。
- 輸出：資源名稱、提供者、零費用證據、登記／會員／資格條件、日期／時段、區域、來源、證據與時間戳。
- 行為：把非金錢條件顯示在卡片上；若直接費用或必要條件無法確認，標為待確認並排除主要排序。

兩條路徑共用來源清單與資料契約，任一路徑無資料時不影響另一條。資料正規化、品質閘門與排序是可測試的 deterministic processing；AI 只在前後協助解析需求與說明理由。

### 7.3 下一階段輸入、預算與協作方向

下一階段將「單次任務預算」擴充為「每月生活預算」，但兩者必須分開顯示：

- **月度生活預算**：使用者設定本月可用總額、剩餘天數、必要支出與各類別上限；系統計算可動用餘額與建議任務上限。
- **單次任務預算**：本次晚餐、採買、活動或交通的硬上限，不能因月度餘額充足而自動放寬。
- **最窮酸模式**：在安全、份量、資格與其他硬限制皆符合後，優先最低可比成本；可接受較多等待、分裝或較低便利性。
- **可以過活模式**：在月預算內平衡成本、時間、份量與使用者偏好，不以極端最低價作唯一目標。
- **個人規則**：將「不能吃／不能用／必要資格」視為硬限制；將口味、品牌、便利性與時段視為軟偏好。過敏等健康相關限制只採用使用者明確輸入，不由系統推測。

協作與社群先分為兩條產品線：

- **團戰合購**：第一階段只支援邀請制熟人小隊，共享目標、數量、截止時間與拆分方式；不代收款、不保證履約。陌生人揪車、即時共乘與路線媒合延後，需另行處理人身安全、責任、保險與法規。
- **社群情報**：一般評價、資料錯誤與安全事件分開回報。食安或身體不適屬高風險通報，只顯示為使用者經驗，直到多方佐證或官方公告；不得由單一留言直接推定因果或觸發永久下架。

完整下一階段範圍、資料模型、信任機制與商業模式假設見 [`RFC-next-phase-budget-squad-community.md`](./RFC-next-phase-budget-squad-community.md)。

## 8. 功能需求

### FR-01：固定區域與匿名入口

- 首頁明確顯示目前區域為「圓山區」。
- 不要求註冊、登入或精確地址。
- 不保存使用者的精確位置；若需要工作階段識別，只使用不含個資的暫時 ID。

### FR-02：最小輸入

支援自然語言與表單兩種入口。最小結構化欄位為：

- 需求／品類；
- 任務預算；
- 使用人數／份量；
- 可接受距離／時間；
- 日期／時段；
- 選填偏好與必要資格。

若資訊不足，系統應指出缺少的欄位或以「待確認」呈現，不應默默猜測。

### FR-03：需求解析與確認

- 顯示解析後的需求、硬限制與軟偏好。
- 使用者可在送出搜尋前編輯解析結果。
- 金額、數量、日期、距離與時間必須保留原始單位並可辨識。

### FR-04：限制優先

- 預算上限、人數／份量、日期、固定區域、最大距離／時間與明確資格是硬限制。
- 任何不符合硬限制的紀錄不能進入主要推薦排序。
- 不得用較低價格抵銷硬限制不符合；例如便宜但份量不足的方案不得標成「最佳」。

### FR-05：並行搜尋

- 送出需求後，UI 要顯示付費選項搜尋 Agent 與免費資源搜尋 Agent 的獨立狀態。
- 兩者應並行開始；一個 Agent 失敗時，另一個仍可完成並顯示部分結果。
- Agent 逾時、來源不可讀或 API 失敗時，顯示原因與可用的人工整理資料，不顯示假成功。

### FR-06：混合資料來源

- 支援人工整理（curated）與網路搜尋（web-searched）資料。
- 每筆資料要標示來源類型，不因是人工整理就省略來源或確認時間。
- Demo 使用的人工整理資料應是公開可核對的固定快照，不得填入虛構商家、價格或活動。

### FR-07：證據品質閘門

- 價格／費用、份量／單位、資格／登記、日期／時段、區域／距離等參與排序的關鍵欄位必須有可讀證據。
- 無法讀出關鍵資訊的紀錄可列在「待確認」，但不得進入主要排序或節省計算。
- 搜尋摘要、模型推測與沒有來源的常識不能單獨作為證據。

### FR-08：正規化與最低成本排序

- 金額統一以 TWD 顯示；必要費用要納入總可比成本。
- 有數量或份量時顯示單位成本；沒有可比份量時只顯示總價並標示限制。
- 同一需求先通過硬限制，再依總可比成本由低至高排序。
- 同價時依可比份量、資料新鮮度與區域／時間符合度作次要排序，並讓理由可見。
- 免費資源不與付費選項混成沒有意義的單一分數；直接費用為零與其他條件分開呈現。

### FR-09：五類橫向分類結果

- 顯示且固定使用五個類別名稱：食品、日用品、免費／公益資源、活動、交通。
- Demo 資料集每類準備 7–10 筆通過證據閘門的可操作資料；畫面最多先顯示 10 筆。
- 若實際搜尋不足 7 筆，顯示實際數量與原因，不用假資料補滿。
- 每類顯示 Agent 來源與資料狀態，讓使用者知道結果是否來自人工整理、網路搜尋或兩者。

### FR-10：結果卡片

每張主要結果卡片至少包含：

- 名稱與提供者；
- 類別；
- 總成本與幣別；
- 單位成本或份量／人數（可取得時）；
- 距離／時間文字或服務時段（可取得時）；
- 必要限制條件；
- 來源類型、來源連結；
- 證據摘錄；
- 搜尋時間與確認時間；
- 資料狀態；
- 節省比較（有可靠基準時）；
- 一個可執行的外部動作，例如購買、報名、查看公告或聯絡提供者。

### FR-11：比較基準與節省

- 節省比較必須顯示基準名稱、基準價格、比較條件與資料時間。
- 可用基準包括使用者原方案、在地常見方案，或使用者明確選擇可用的 Costco 基準。
- 節省金額為基準總可比成本減去推薦總可比成本；比例分母為基準總可比成本。
- 若基準、價格、份量或必要費用不完整，顯示「無足夠資料計算節省」，不得虛構金額／比例。

### FR-12：清單、收藏、分享與回報

- 使用者可將結果加入暫時清單與收藏。
- 匿名模式下，收藏 ID 與必要結果快照保存在目前瀏覽器；不得暗示已跨裝置同步。登入後以 ID 聯集合併至帳號，D1 寫入成功才清除本機副本。
- 分享內容應包含需求摘要、結果名稱、來源與資料時間；不包含精確位置或不必要個資。
- 使用者可回報過期價格、錯誤條件、來源失效或分類錯誤。

### FR-13：例外與空結果

- 沒有符合硬限制的結果時，說明是哪個限制造成空結果，並讓使用者選擇放寬限制。
- 來源衝突時顯示衝突，採較新且較權威來源；無法判定時排除排序。
- 過期資料仍可作為線索，但要標示過期，不能冒充目前可用。
- 單一 Agent 失敗時保留另一 Agent 的結果與狀態。

### FR-14：明確排除導航與健康判斷

- 交通結果不得提供導航按鈕、路線規劃或轉向指示。
- 食品結果不得推導健康分數、營養建議、醫療建議或未查證營養數值。
- UI、Demo 腳本與文案不可暗示上述功能已完成。

## 9. 資料與證據規則

### 9.1 候選紀錄最小資料契約

每筆資料至少應能表達以下欄位；欄位名稱可在實作時映射成其他 schema：

```text
id
category
title
provider
area
price_total_twd
price_unit
quantity_or_servings
mandatory_fees
eligibility
registration_required
availability_or_event_time
distance_or_time_text
source_url
source_type              # curated | web-searched
source_authority         # official | provider | public | other
evidence_quote
collected_at
verified_at
data_status
agent
action_url
```

免費資源可將 `price_total_twd` 設為 0，但只有在來源明確表示無直接費用時才可如此設定；登記、會員、資格、押金、材料費或名額條件仍要放在 `eligibility` 或對應欄位。

### 9.2 來源與證據優先順序

1. 官方公告、官方活動頁或提供者正式頁面。
2. 公共機關、場館、社區或公益組織的正式資訊。
3. 可辨識提供者且有日期的可靠公開頁面。
4. 搜尋結果只作為找線索；不能取代原始頁面中的關鍵證據。

每筆結果都要顯示來源 URL、來源類型、證據摘錄、`collected_at` 與 `verified_at`。若頁面沒有可讀關鍵欄位，狀態設為「部分驗證／待確認」或「無法納入比較」。

### 9.3 價格與比較規則

- `總可比成本 = 商品／服務價格 + 必要費用 - 明確適用折扣`。
- 不把未知運費、服務費、押金或會員費當作 0。
- 優惠只有在使用者符合來源列出的條件時才可套用。
- 不同份量、人數、包裝或服務內容不得直接宣稱誰比較便宜。
- 單位成本要說明單位，例如每人、每份、每公升或每件。
- 「最低成本」指在本次搜尋範圍、已知來源與已套用限制內最低，不代表全網保證最低。

### 9.4 時間、距離與可用性

- 同時記錄頁面／公告上的有效時間（若有）與系統搜尋／確認時間。
- 距離／時間若由來源提供，保留來源原文；若為估算，必須標示「估算」及估算方式。
- 不使用未經使用者同意的精確定位，不在 MVP 產生路線。
- 不承諾即時庫存、即時名額、營業狀態或交通即時到站。

### 9.5 衝突、過期與缺欄位

- 官方來源與轉載來源衝突時，優先官方來源；同一來源以較新且仍在有效期的內容為準。
- 兩個權威來源仍衝突時，顯示「衝突待確認」，不進主要排序。
- 價格、日期、資格或費用缺失時，不推導或補值。
- 來源超過其明示有效期，或無法確認仍有效時，標示「過期／待確認」。

### 9.6 授權與資料責任

- 只使用團隊有權使用的公開資料、人工整理內容與可核對來源。
- 儲存必要的結構化欄位與短證據摘錄，不大量複製來源頁面。
- 外部連結回到原始提供者，並在 UI 提醒使用者以原始頁面為準。
- 任何供應商、活動主辦者或公共機構的名稱與價格都必須能追溯。

## 10. 非功能需求

### NFR-01：Mobile-first

- 先以手機直向版面設計；支援至少 320px 寬度的現代瀏覽器。
- 主要流程不依賴 hover；卡片、證據抽屜與外部動作適合觸控。
- 內容在桌面寬度仍可閱讀，但不是優先驗收目標。

### NFR-02：可感知效能

- 使用者送出後立即看到需求解析、catalog、證據與排序進度，不顯示空白等待頁。
- 準備好的 Demo 環境以 15 秒內呈現第一批可用結果為目標。
- 任一 Agent 超時時先呈現另一 Agent 或固定整理資料；不可無限等待。

### NFR-03：可理解與可及性

- 使用清楚的繁體中文，必要時保留 English technical terms。
- 重要狀態不只靠顏色表達；使用標籤、圖示替代文字或明確文案。
- 主要文字、來源、價格與限制在手機上不需水平捲動即可閱讀。
- 互動元件具可辨識 focus、足夠觸控尺寸與語意化標題。

### NFR-04：透明與可追溯

- 使用者可從推薦卡片一路查看來源、證據與時間。
- AI 解析、搜尋結果、正規化與排序狀態要能由團隊在 Demo 中解釋。
- UI 不將「已找到」寫成「官方保證」或「即時保證」。

### NFR-05：隱私與安全

- 不要求或儲存精確地址、GPS、姓名、電話或付款資料。
- 預設不保存自然語言輸入原文；若為錯誤排查需暫存，應去除個資並設定短保留期。
- 外部連結應清楚標示離開 ALL in life，並避免未經確認的自動操作。

### NFR-06：成本與退化

- 對網路搜尋設定來源、查詢數與時間上限，避免無限制 API 成本。
- 使用固定整理資料作為 Demo fallback，但仍保留證據與確認時間。
- 任何 partial result 都標示完成度與失敗原因，不用模型生成內容掩蓋資料缺口。

## 11. 驗收條件（Definition of Done）

以下條件全部達成，才算 MVP Demo ready：

1. **產品識別**：頁面、Demo 與文件只使用產品名稱「ALL in life」，並明確顯示固定區域「圓山區」。
2. **匿名入口**：手機瀏覽器可直接使用，不註冊、不要求精確位置，不保存敏感位置資料。
3. **輸入可控**：自然語言與表單至少能表達需求、預算、人數／份量、距離／時間與日期；送出前看得到解析摘要。
4. **安全雙路徑**：畫面能說明付費與零元候選分流；AI 不可用時仍保留 catalog、硬限制與規則排序。
5. **五類結果**：橫向分類列有食品、日用品、免費／公益資源、活動、交通五類；真實筆數依資料庫回傳，Demo 固定情境獨立運作。
6. **限制先行**：給定預算、份量／人數、日期、區域與距離／時間後，不符合硬限制的候選不進主要排序。
7. **最低可比成本**：付費結果依可比總成本排序，並能解釋總價、單位／份量與必要費用；未知費用不當作零。
8. **證據可見**：每個主要結果都有來源、證據摘錄、來源類型、搜尋／確認時間、資料狀態與外部動作。
9. **節省可驗證**：至少一個 Demo 情境能以已知基準顯示節省金額／比例；基準不足時 UI 明確顯示無法計算，而非補數字。
10. **免費資源可行動**：至少一筆免費／公益資源明確顯示直接費用為零、登記／資格／時段條件、來源與下一步連結。
11. **例外透明**：能示範或至少在測試資料中處理缺欄位、來源衝突、過期、Agent 逾時與無結果。
12. **範圍守門**：Demo 中沒有導航、路線規劃、健康／營養／醫療建議、即時庫存保證或虛構來源。

### 驗收用最小測試案例

- **Case A：預算與人數**
  - Given：2 人、NT$300 上限、圓山區、20 分鐘／2 公里內。
  - When：查找食品。
  - Then：只出現符合限制且有價格與份量證據的結果；排序可由成本解釋。

- **Case B：免費但有條件**
  - Given：週末、直接費用為零、可接受先登記。
  - When：查找活動或公益資源。
  - Then：至少一筆卡片清楚區分「免費」與登記／資格／名額條件。

- **Case C：缺少基準**
  - Given：結果有價格，但沒有同份量的原方案或常見方案。
  - When：查看節省。
  - Then：顯示無足夠資料計算，不顯示推測比例。

- **Case D：來源衝突**
  - Given：兩個來源的費用或時間不同。
  - When：查看結果。
  - Then：採較新且較權威來源；無法判斷時標為衝突並排除主要排序。

## 12. 風險與應對

- **資料過期**：價格、名額與活動資訊可能改變。每筆顯示時間，使用固定快照作 Demo fallback，不承諾即時狀態。
- **價格不可比**：包裝、份量、會員價或必要費用不同。顯示比較單位與條件；不可比就不做節省計算。
- **搜尋結果幻覺**：模型可能補出不存在的店家或價格。所有主要欄位必須有來源證據，無證據不排序。
- **免費資源誤解**：免費可能仍需登記、資格、會員、押金或材料費。把條件放在卡片前段，不只顯示醒目的「免費」。
- **來源授權問題**：網頁內容未必可任意複製。只保存必要欄位與短摘錄，保留原始連結並確認使用條款。
- **Agent 延遲／API 成本**：限制搜尋範圍、並行執行、設置 timeout、使用已驗證的固定資料 fallback。
- **圓山區範圍模糊**：Demo 先固定團隊定義的生活圈與邊界文字，資料集中的 `area` 必須一致；不暗示全台適用。
- **匿名收藏只在單一瀏覽器**：UI 明示裝置範圍；登入合併不得覆寫既有帳號收藏，且 D1 寫入失敗時保留本機副本。
- **範圍膨脹**：健康、營養、導航、交易與更多地區列入 backlog；Demo 只驗收本 PRD 的閉環。

## 13. 60–90 秒 Demo 故事線

### 0–10 秒：提出問題

「在圓山區臨時要解決一個日常需求，使用者通常要分別查價格、份量、活動條件與免費資源，還要自己判斷哪些資訊可信。ALL in life 把這些限制放進同一個決策流程。」

### 10–20 秒：輸入需求

輸入：「今天晚餐，2 人，預算 NT$300，圓山區，20 分鐘／2 公里內，可外帶。」展示解析後的預算、人數、區域與限制，快速確認後送出。

### 20–35 秒：展示 AI 解析與安全資料路徑

同時展示：

- 付費選項搜尋 Agent：找符合成本與份量的選項；
- 免費資源搜尋 Agent：找直接費用為零但可能需要登記或資格的資源。

強調 AI 只整理需求，資料回來後仍要經過證據與限制檢查。

### 35–52 秒：展示五類橫向分類

快速滑過食品、日用品、免費／公益資源、活動、交通五個類別。指出每類有 7–10 筆資料、每筆標示來源類型與資料狀態；不要花時間逐張讀完。

### 52–68 秒：打開結果與證據

點開一張食品或日用品卡片，展示總成本、單位／份量、必要條件、來源 URL、證據摘錄、確認時間與外部動作。指出「便宜」是通過限制與可比欄位後才成立。

### 68–80 秒：展示節省

切換到有可靠基準的結果，展示節省金額／比例與基準名稱。若示範資料沒有足夠基準，反而展示「無足夠資料計算」來證明產品不虛構數字。

### 80–90 秒：展示免費資源與邊界

打開一筆免費／公益資源，指出直接費用為零，但登記／資格／時段仍清楚可見。收尾說明：這版不做導航、不做健康／營養判斷、不保證即時庫存；下一步是擴大資料與驗證能力。

## 14. Hackathon 團隊執行順序

1. **先凍結資料契約**：確認五類欄位、狀態值、證據格式與比較基準規則。
2. **先做可信資料**：每類整理 7–10 筆可核對紀錄，標示 curated、來源與時間；再接 web-searched enrichment。
3. **接輸入與解析**：自然語言與表單共用同一個結構化需求。
4. **接 AI 安全層與雙資料路徑**：先讓 schema、timeout、partial result 與 fallback 可展示，再增加搜尋廣度。
5. **做正規化與排序**：先硬限制，再最低可比成本；將無證據、衝突與過期資料隔離。
6. **完成手機分類結果**：五類、結果卡、證據抽屜、外部動作與錯誤狀態。
7. **跑驗收案例與 Demo 排練**：用固定輸入重播，確認每個數字都能回到來源，並在 90 秒內完成故事線。

## 15. 後續路線圖

### Phase 1：Demo 後的可靠性

- 自動來源刷新與過期偵測。
- 更完整的衝突比對與資料品質儀表板。
- 更多圓山區資料與實際使用者回報流程。
- 可解釋的排序偏好與更好的部分結果處理。

### Phase 2：擴大生活圈與個人化

- 使用者明確同意後的地區選擇與位置權限。
- 更多行政區與跨區比較。
- 個人預算、常用份量、會員資格與收藏檔案。
- 更完整的商家、活動主辦者與公共資源合作資料。

### Phase 3：延後能力

- 健康／營養資訊：需可靠資料、清楚免責與專業審核，不從 MVP 的食品價格資料直接推導。
- 導航與路線：需位置權限、地圖／交通資料、即時狀態與新的隱私設計。
- 交易整合：付款、下單、票券與庫存需與提供者正式整合。
- 即時價格、名額與庫存：需來源 API 或持續驗證機制。

## 16. 最終成功定義

ALL in life 的 MVP 不以「功能最多」或「涵蓋所有生活」成功，而以以下閉環成功：

> 一位匿名使用者在圓山區輸入有預算與限制的日常需求，AI 把文字整理成可編輯條件，系統再從五類資料中找出有證據的可行選項，讓使用者理解為何符合限制、能否省下明確金額，以及下一步該查看哪個原始來源。

只要這個閉環可在手機上穩定重播、資料不造假、限制與證據可解釋，ALL in life 就具備可供評審理解、團隊開發與後續擴展的 Hackathon MVP。
