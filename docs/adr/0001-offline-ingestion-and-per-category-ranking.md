# 資料事先匯入，Agent 只做按類別並行的推薦排序

PRD v0.2 原本設計兩個 Agent 在執行期上網搜尋。我們改為：候選紀錄、來源與證據由爬蟲或 API 腳本在搜尋之前匯入本機 PostgreSQL；搜尋時先跑一次 deterministic 的第一階段篩選（證據閘門 + 硬限制），再由付費選項 Agent 與免費資源 Agent 並行做推薦排序，每個 Agent 內部按類別各打一次 LLM。理由：執行期搜尋會讓「無證據不排序」無法保證、API 成本不可控、Demo 延遲不可預測；事先匯入讓每筆資料都經過人工可核對，Agent 只能回傳輸入清單裡的 id，幻覺無處落地。按類別並行是因為 LLM 輸出 token 是延遲主因，五個約 8 筆的呼叫比一個 40 筆的呼叫快數倍，且單一類別失敗只影響該類。

## Considered options

- 執行期網路搜尋 Agent（PRD 原案）：廣度高，但證據與成本不可控。
- 兩個 Agent 各一次 LLM 呼叫：程式最少，但付費側一次排 25 筆延遲最長、一掛全掛。
- 五個 Agent 各對應一類：速度與隔離同本案，但畫面與 PRD 都要改成五個 Agent；改為在兩個 Agent 內部按類別並行即可得到同樣效果。

## Consequences

- 資料匯入成為獨立作業，需要另外的來源清單與腳本；沒有匯入資料就沒有結果。
- 「web-searched」只描述資料的來源方式，不代表執行期有搜尋。
- 換回執行期搜尋只需在第一階段篩選之前多一個資料來源，Agent 契約不變。
